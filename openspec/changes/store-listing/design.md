## Context

Unitary is published on Google Play's closed track.  The listing has a
placeholder description typed into the Play Console and the README's phone
screenshots, which are downscaled to 480 px wide.  It has no feature graphic
and no tablet screenshots.  The maintainer's mockup of the feature graphic
shows a dark navy gradient, the app icon, the "Unitary" wordmark in a
condensed bold face, the tagline "Unit conversion & dimensional analysis", and
a phone showing the Length worksheet in the dark theme.

Existing pieces this change builds on:

- `tool/generate_icons.sh` renders `assets/icon/unitary.svg` with Inkscape.
  The SVG names its font in an `@font-face` rule, but the script's comments
  say the font must be available to fontconfig.  The `generate-icons`
  pre-commit hook reruns it when its sources change, and the CI lint job skips
  that hook (`SKIP: generate-icons`) because runners have no Inkscape.
- `tool/take_screenshots.sh` boots the `Pixel_6_Pro_API_33_13.0_` emulator if
  no device is connected, and runs `integration_test/screenshots/take_screenshots.dart`
  through `flutter drive` with `test_driver/screenshots_driver.dart`.  It then
  downscales the images in `doc/screenshots/` with ImageMagick.  The driver
  always writes to `doc/screenshots/`.  The capture flow navigates the phone
  layout only: the drawer, the worksheet AppBar dropdown, and a pushed unit
  detail page.
- Installed locally: the API 35 `google_apis` x86_64 system image, Inkscape,
  ImageMagick, and `avdmanager` under the SDK's `cmdline-tools/latest`.
  `avdmanager` writes AVDs to `~/.config/.android/avd`, but the emulator reads
  `~/.android/avd` on this machine (found during the `apk-size` change).

Play's requirements, from its help page on preview assets (checked September
29, 2026):

| Asset                | Format                       | Size                                                      | Count          |
|----------------------|------------------------------|-----------------------------------------------------------|----------------|
| App icon             | 32-bit PNG with alpha        | 512×512, ≤1024 KB                                         | 1              |
| Feature graphic      | JPEG or 24-bit PNG, no alpha | 1024×500                                                  | 1              |
| Phone screenshots    | JPEG or 24-bit PNG, no alpha | 320–3840 px per side; 9:16 or 16:9 at ≥1080 px to promote | ≥4 to promote  |
| Tablet screenshots   | JPEG or 24-bit PNG, no alpha | 1080–7680 px per side, 9:16 or 16:9                       | ≥4 per size    |
| Short description    | Text                         | ≤80 characters                                            | –              |

The help page does not state the other text limits.  Play has long allowed 30
characters for the app name and 4,000 for the full description; the Console
enforces both when the text is pasted in.

Every stock tablet profile available locally has a 16:10 screen (Nexus 7 2013
at 1200×1920, Pixel Tablet at 2560×1600), so none of them produces an
acceptable tablet screenshot as is.

## Goals / Non-Goals

**Goals:**

- The store text, icon, feature graphic, and screenshots live in the
  repository, in a layout upload tools understand.
- Every image can be regenerated by a script from committed sources.
- A test fails when committed store assets break Play's requirements.
- The tablet screenshots show the two-pane layouts.
- The README screenshots and their capture are unchanged.

**Non-Goals:**

- Uploading to Play from CI, or with any tool.  Files are copied into the
  Console by hand.
- Per-release "What's new" text, translations, and Chromebook screenshots.
- Rendering the graphics or capturing screenshots in CI.  Both need tools and
  an emulator that the runners do not have, which is why the icon hook is
  already skipped there.

## Decisions

### D1: Fastlane metadata layout, plain text

Everything goes under `fastlane/metadata/android/en-US/`:

```
title.txt
short_description.txt
full_description.txt
images/icon.png
images/featureGraphic.png
images/phoneScreenshots/NN_<name>.png
images/sevenInchScreenshots/NN_<name>.png
images/tenInchScreenshots/NN_<name>.png
```

This is the layout fastlane `supply` and Gradle Play Publisher read and write,
and the one F-Droid reads.  Adopting it costs nothing now and keeps automated
uploads, or an F-Droid listing, a matter of configuration later.  The `NN_`
prefix fixes the order in which the screenshots appear.

The description is plain text.  Play renders line breaks and accepts a few
HTML tags, but the other readers of this layout treat HTML differently.
Bullets are written as `•` lines.

**Alternative rejected:** generating the text from `README.md`.  The README is
written for GitHub, with tables, images, and build instructions, and its reader
already knows what the project is.  A store reader does not.  Generating from
it would need markers in the README and a converter, to produce text that
should be written differently anyway.

### D2: A check library with a test against the committed tree

`tool/check_store_listing_lib.dart` holds pure functions:

- read a PNG's width, height, bit depth, and colour type from its `IHDR`
  chunk, with no image dependency;
- check a text file's length in Unicode characters (runes) against a limit;
- check one image against a named requirement (icon, feature graphic, phone,
  tablet) and a screenshot folder against its count limits.

`test/tool/check_store_listing_lib_test.dart` tests those functions with
synthetic inputs, and one test runs them against the real
`fastlane/metadata/android/en-US/` tree.  That test makes `flutter test`, and
so CI, fail when a committed asset breaks a rule.  The same pattern already
protects the README's links in `generate_web_docs_lib_test.dart`.

No executable is added: nothing needs the check outside the test suite.

Rules checked:

| Asset             | Rule                                                                                         |
|-------------------|----------------------------------------------------------------------------------------------|
| `title.txt`       | 1–30 characters, one line                                                                     |
| Short description | 1–80 characters, one line                                                                     |
| Full description  | 1–4000 characters                                                                             |
| Icon              | 512×512, 8-bit RGBA (colour type 6), at most 1024 KB                                          |
| Feature graphic   | 1024×500, 8-bit RGB (colour type 2)                                                           |
| Phone screenshots | 8-bit RGB; 9:16 or 16:9; short side ≥1080, long side ≤3840; 4–8 files                         |
| Tablet sets       | 8-bit RGB; 9:16 or 16:9; each side 1080–7680; 4–8 files per set                               |

The 1080 px phone minimum and the 4-file phone minimum are Play's conditions
for promoting an app, not for listing it.  They are enforced anyway, so the
listing stays eligible.  Eight is the most screenshots Play shows per device
type.  An aspect ratio counts as 16:9 when `long × 9 == short × 16` exactly,
which every profile in D4 satisfies.

### D3: Store graphics rendered by a script, with a pre-commit hook

`tool/generate_store_graphics.sh` renders both images with Inkscape and
post-processes them with ImageMagick:

- **Icon:** `assets/icon/unitary.svg` at 512×512, written as 32-bit RGBA
  (`PNG32:`).
- **Feature graphic:** `assets/store/feature_graphic.svg` at 1024×500, then
  flattened onto its background colour with the alpha channel removed, written
  as 24-bit RGB (`PNG24:`).

Both images are written with `-strip`.  Without it ImageMagick records
creation and modification times in each PNG, so every run produced a
different file from identical pixels, and the hook below would have churned
the committed images on every source change.  The screenshot post-processing
strips them for the same reason.

A `generate-store-graphics` pre-commit hook runs the script when the feature
graphic SVG, its font, the icon SVG, the linked screenshot, or the script
changes.  The CI lint job adds the hook to `SKIP`, as it does for
`generate-icons`, because the runners have no Inkscape.  D2's test still
checks the committed PNGs in CI.

### D4: The feature graphic: layout, font, and phone image

`assets/store/feature_graphic.svg` has a 1024×500 canvas and follows the
mockup:

- **Background:** a vertical gradient in the navy of the mockup.
- **Icon:** placed with an `<image>` referring to `../icon/unitary.svg`, so the
  graphic follows any change to the icon.  If Inkscape cannot render a nested
  SVG at the quality needed, the fallback is the rendered `icon.png` from D3,
  which the script renders first.
- **Wordmark and tagline:** SVG `<text>` in a bundled OFL font, kept as text,
  not converted to paths, so the wording can be edited.
- **Phone:** a device frame drawn in the SVG (rounded body, bezel, camera dot)
  with an `<image>` of the Length worksheet from the phone screenshot set,
  clipped to the screen area.

**Font.** The candidates are Anton and Oswald, both SIL Open Font License
condensed faces with lowercase letters; Bebas Neue is capitals only, and the
mockup's wordmark is not.  Both are rendered into the layout and compared with
the mockup, and the closer one is kept.  Its `.ttf` and `OFL.txt` go in
`assets/store/fonts/`, which is not a Flutter asset directory, so the app does
not ship it.

**Font loading.** The script points Inkscape at a temporary fontconfig file
that includes the system configuration and adds `assets/store/fonts/`, so the
font need not be installed.  Before rendering, it checks with `fc-match` under
the same configuration that the family resolves to the bundled file, and fails
if it does not.  Otherwise a missing font would silently render the graphic in
a fallback face.

**Phone image.** The `<image>` refers to the committed phone screenshot by
relative path.  Re-capturing the phone set therefore changes the graphic at the
next render, which the pre-commit hook triggers because the screenshot is one
of its inputs.

### D5: Emulator profiles with exact 16:9 screens

The capture script creates three AVDs from the API 35 `google_apis` x86_64
image, if they do not exist, and overrides the screen in each `config.ini`
(`hw.lcd.width`, `hw.lcd.height`, `hw.lcd.density`):

| AVD                      | Screen (px)    | Density | Size in dp       | App layout                        |
|--------------------------|----------------|---------|------------------|-----------------------------------|
| `Unitary_Store_Phone`    | 1080×1920      | 420     | 411×731          | compact: drawer, one pane         |
| `Unitary_Store_Tablet7`  | 1080×1920      | 240     | 720×1280         | medium: drawer, two panes         |
| `Unitary_Store_Tablet10` | 2560×1440 (landscape) | 320 | 1280×720  | expanded: navigation rail, two panes |

All three are exact 9:16 or 16:9 and within Play's size ranges, and each lands
in a different layout tier of `WindowSizeClass` (compact below 600 dp, medium
600–1040, expanded above 1040), so the three sets show three different
layouts.  The base device profiles are `pixel_2`, `Nexus 7 2013`, and
`pixel_tablet`, which only supply the frame and hardware defaults.

The script sets `ANDROID_AVD_HOME=~/.android/avd` for both `avdmanager` and
the emulator, so the AVDs it creates are the ones the emulator finds.

**Alternatives rejected:** using the stock 16:10 profiles and cropping or
padding the captures to 16:9.  Cropping removes part of the interface;
padding adds bars that look like a broken screenshot.

### D6: One capture flow for every target, navigating by layout

The capture Dart file runs one flow and adapts to the layout it finds, rather
than keeping a separate script per device:

- **Page navigation:** tap the destination on the `NavigationRail` if one is
  present, otherwise open the drawer.
- **Worksheet selection:** use the AppBar dropdown if present, otherwise tap
  the template in the list pane.
- **Unit detail:** after tapping a unit, go back only if a route was pushed.
  On tablets the detail is in the right pane and is captured with the list.

Which captures a run takes is chosen by `--dart-define=SCREENSHOT_SET=` with
values `readme`, `phone`, and `tablet`.  `readme` keeps today's sequence
exactly.  The store sets:

| Set                | Captures                                                                 |
|--------------------|--------------------------------------------------------------------------|
| phone              | freeform, worksheet (Length), currency, browser, unit detail, settings   |
| tablet (7" and 10")| freeform with history, worksheet (Length), currency, browser with detail, settings |

On tablets, freeform shows its history pane, which is empty after the fresh
start the capture begins with, so the tablet flow first runs a few conversions
to fill it.

The driver writes to the directory in the `SCREENSHOT_DIR` environment
variable, defaulting to `doc/screenshots/`, so the README path is unchanged.

`tool/take_screenshots.sh` takes a target argument:

- no argument or `readme`: today's behaviour, unchanged;
- `phone`, `seven-inch`, `ten-inch`: boot that AVD, set the dark theme
  (`cmd uimode night yes`), capture into `build/screenshots/<target>/`,
  remove the alpha channel from each image, and replace the matching fastlane
  folder's contents with the results, numbered in capture order;
- `store`: all three store targets in turn.

Each store target boots its own emulator and shuts it down afterwards, since
three emulators at once would not fit comfortably on the development machine,
and the existing rule stands: an emulator is shut down only if the script
started it.

### D7: Store text

The title is **"Unitary: Unit Converter"** (23 characters): the name, plus what
people search for.

The short description says what the app does and what makes it different in
one line.  The full description:

1. opens with what the app does, in terms a newcomer understands;
2. says early that there are no ads, trackers, subscriptions, or in-app
   purchases, and that everything works offline;
3. then covers freeform expressions with dimensional analysis, worksheets,
   the unit browser, currency rates, and the tablet layouts and accessibility;
4. ends with the licence and a link to the source code.

It makes no claim the privacy policy does not support.  It says the app
collects no personal data, not that it makes no network requests, since it
fetches exchange rates.  It does not repeat the policy's disclosures, such as
which service supplies the rates: the listing is for deciding whether to
install, and the policy and Play's Data safety declaration carry those
details.

## Risks / Trade-offs

**[Emulator output varies between runs]** → The system status bar is not an
issue: the capture records only the Flutter surface, so the clock, battery,
and notifications never appear (found on the first capture, which is why
SystemUI demo mode is not used).  The app content is deterministic because
each capture starts from cleared preferences, and currency values come from
the built-in rates because the capture seeds a fresh rate timestamp and never
fetches.  The one exception is the Currency worksheet's banner, which shows
that seeded timestamp, so it reads the time of capture.  A fixed older
timestamp would instead trigger a real rate fetch, since the app refreshes
rates more than a day old.

**[Rendered PNGs differ between tool versions]** A different Inkscape or
ImageMagick version could render different bytes from the same source, so the
pre-commit hook could produce a diff on another machine.  → The hook only runs
when a source changes, and the resulting PNG is reviewed like any other change.
This is the same trade-off `generate-icons` already makes.

**[The feature graphic depends on the phone screenshot]** Re-capturing the
phone set changes the graphic.  → Intended: the graphic shows the current app.
The hook lists the screenshot as an input, so the two cannot drift apart
silently.

**[Custom `hw.lcd` values may be ignored]** If the emulator ignored the
overridden screen, the captures would come out at the base profile's size.  →
The capture script prints each image's size, and D2's test rejects any size
that is not 9:16 or 16:9 within range.

**[Play's rules change]** → The check library keeps every limit in one place,
and D2 records the date the rules were read.

## Migration Plan

1. Add the check library and its tests, with the real-tree test expecting the
   new tree.
2. Build the capture targets and AVD setup; capture the three store sets.
3. Build the feature graphic and the store icon; add the hook and the CI skip.
4. Write the store text.
5. Replace the placeholder listing in the Play Console with the committed text
   and images, by hand.

Rollback: delete the new files and revert the scripts.  The Play Console keeps
whatever was last uploaded until it is replaced.
