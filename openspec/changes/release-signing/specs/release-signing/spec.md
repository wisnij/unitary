## ADDED Requirements

### Requirement: Release artifacts are signed with the app signing key

Release builds SHALL be signed with the project's app signing key and MUST NOT be
signed with the Android debug key.  The signing configuration SHALL read its
credentials from an untracked `android/key.properties`, following the standard
Flutter convention, so that no key material or password appears in a tracked
file.

The app signing key SHALL be RSA 2048 with signature algorithm SHA256withRSA,
stored in a PKCS12 keystore, and valid for 30 years from generation.  Its
certificate distinguished name SHALL carry a minimal field set — common name,
organization, and country — omitting locality and state, since certificate fields
are permanently public and cannot be retracted.

#### Scenario: A release build carries the app signing certificate

- **WHEN** a release APK is built by the release workflow
- **THEN** `apksigner verify --print-certs` reports the app signing key's
  certificate, and its SHA-256 fingerprint equals the recorded expected value

#### Scenario: No release artifact is debug-signed

- **WHEN** any artifact published to a GitHub release or uploaded to Play is
  inspected
- **THEN** its signer certificate distinguished name is not `C=US, O=Android,
  CN=Android Debug`

### Requirement: Separate upload key for Play uploads

The key used to authenticate uploads to Google Play SHALL be distinct from the
app signing key, so that a compromised upload key can be rotated through the Play
Console without abandoning the app's identity.  Both keys SHALL be stored in
separate keystore files rather than as two aliases within one keystore, so that
possession of one keystore's password does not grant access to the other key.

#### Scenario: The two keys are distinct

- **WHEN** the app signing keystore and the upload keystore are inspected
- **THEN** they are separate files, and their certificates have different SHA-256
  fingerprints

#### Scenario: Each artifact is signed with its designated key

- **WHEN** the release workflow builds both the GitHub APK and the Play app
  bundle in the same run
- **THEN** the APK is signed with the app signing key and the app bundle is
  signed with the upload key

### Requirement: Both distribution channels share one certificate

A given version SHALL present the same signing certificate whether it was
obtained as an APK attached to a GitHub release or installed from the Play
Store, so that a user who installed from one channel can update from the other.
This SHALL be achieved by enrolling in Play App Signing with the project's own
app signing key rather than one generated by Google.

#### Scenario: Play reports the project's own certificate

- **WHEN** Play App Signing enrolment is complete
- **THEN** the app signing certificate shown in the Play Console has the same
  SHA-256 fingerprint as the locally held app signing key

#### Scenario: A Play install accepts a GitHub APK as an update

- **WHEN** a user has the Play-delivered build of a version installed, and
  installs the GitHub APK of a later version
- **THEN** the installation succeeds as an update rather than being rejected for
  a signature mismatch

### Requirement: Key material never enters the repository or build output

Keystores, `key.properties`, and signing passwords SHALL NOT be committed,
included in any build artifact, or written to workflow logs.  The repository's
ignore rules SHALL cover keystore files and `android/key.properties` so that a
keystore placed in the working tree cannot be committed accidentally.

#### Scenario: Ignore rules cover key material

- **WHEN** a keystore file or `android/key.properties` is present in the working
  tree
- **THEN** `git status` does not offer it as an untracked file to be added

#### Scenario: Built artifacts contain no key material

- **WHEN** a signed release APK is inspected
- **THEN** it contains no keystore file and no `key.properties`

#### Scenario: Workflow logs contain no key material

- **WHEN** the release workflow completes
- **THEN** its logs contain neither a decoded keystore nor any signing password

### Requirement: Developer builds succeed without signing keys

A clone with no keystore and no `android/key.properties` SHALL still build, so
that contributors and CI jobs that do not publish are unaffected.  The release
signing configuration SHALL be applied only when `android/key.properties` is
present, falling back to the debug signing configuration otherwise.

#### Scenario: Building without key.properties

- **WHEN** a developer with no `android/key.properties` builds the app
- **THEN** the build succeeds using the debug signing configuration

#### Scenario: Building with key.properties present

- **WHEN** `android/key.properties` is present and names a valid keystore
- **THEN** the release build is signed with the key it designates

### Requirement: The release workflow verifies which key was used

The release workflow SHALL verify the signature of the artifact it produced and
SHALL fail when that signature does not match the expected app signing
certificate.  This matters because a missing or misconfigured
`android/key.properties` causes a silent fallback to debug signing rather than a
build failure, so a wrong-key build is a plausible outcome rather than a
hypothetical one.  Verification SHALL compare the certificate's SHA-256
fingerprint against a recorded expected value; asserting only that the
certificate is not the debug certificate is insufficient, because that would pass
for any wrong-but-real key.

#### Scenario: Correctly signed artifact passes verification

- **WHEN** the release workflow builds an APK signed with the app signing key
- **THEN** the verification step finds the expected certificate fingerprint and
  the workflow proceeds

#### Scenario: Debug-signed artifact fails the workflow

- **WHEN** the signing configuration falls back to debug signing because
  `android/key.properties` is missing or malformed
- **THEN** the verification step fails and the release workflow fails before
  publishing any artifact

#### Scenario: Wrong-key artifact fails the workflow

- **WHEN** the artifact is signed with a real key whose certificate fingerprint
  differs from the expected value
- **THEN** the verification step fails and the release workflow fails before
  publishing any artifact
